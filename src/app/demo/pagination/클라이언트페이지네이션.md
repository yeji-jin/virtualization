# 라이브러리 없이 이해하는 클라이언트 페이지네이션

실습 코드: [pagination-lab.tsx](./pagination-lab.tsx)  
실습 경로: `/demo/pagination`  
관련 노트: [직접 구현한 가상화](../virtualization/라이브러리없는버전.md)

## 1. 무엇을 최적화하는가?

클라이언트 페이지네이션은 전체 데이터를 배열에 보관하고, 현재 페이지에 해당하는 데이터만 선택해 렌더링한다.

```text
전체 items: 10,000개
현재 pageItems: 20개
화면의 목록 행: 20개
```

데이터가 배열에서 삭제되는 것은 아니다. slice는 원본 배열을 유지하고 선택한 구간을 새 배열로 반환한다. 객체 자체를 깊게 복사하는 것도 아니다.

전체 데이터를 API로 받는 경우 초기 다운로드, JSON 처리, 원본 배열의 메모리 비용은 남는다. 페이지를 바꿀 때는 이미 받은 배열을 사용하므로 페이지 이동 자체에 추가 API 요청이 필요하지 않다. 현재 실습은 API 없이 createItems로 mock data를 만든다.

## 2. 먼저 세 가지 번호를 구분하기

| 구분 | 시작 값 | 예 |
|---|---|---|
| 페이지 번호 page | 1 | 1페이지, 2페이지 |
| 배열 인덱스 | 0 | items[0]이 첫 번째 데이터 |
| 사용자에게 보여주는 순번 | 1 | 인덱스 10은 11번째 데이터 |

실습 데이터의 id는 1부터 생성되지만, 일반적으로 ID와 배열 위치는 별개다. 페이지 범위는 ID가 아니라 배열의 현재 순서를 기준으로 계산한다.

## 3. 주요 변수와 함수

| 이름 | 의미 |
|---|---|
| count | 전체 데이터 개수. 초기 1,000 |
| page | 현재 페이지. 초기 1 |
| pageSize | 페이지 하나에 보여줄 최대 개수. 초기 20 |
| items | 전체 원본 데이터 배열 |
| totalPages | 필요한 전체 페이지 수 |
| start | 선택할 시작 인덱스. 포함 |
| end | 선택할 끝 경계. 미포함 |
| pageItems | 현재 페이지에서 렌더링할 데이터 |
| firstPageButton | 화면에 표시할 첫 번째 페이지 번호 버튼 |
| pageNumbers | 페이지 번호 버튼들의 배열. 실제 데이터가 아님 |
| goToPage(nextPage) | 요청한 페이지를 유효한 범위로 제한하고 상태 변경 |
| createItems(count) | 가짜 데이터 생성 |
| format(value) | 숫자를 읽기 쉬운 문자열로 변환. 1000 → "1,000" |
| buttonClass | 공통 버튼 스타일 |

setCount, setPage, setPageSize는 각각의 상태 변경 함수다.

```tsx
const items = useMemo(() => createItems(count), [count]);
```

일반적인 재렌더링에서는 count가 같으면 배열 생성 결과를 재사용한다. 페이지 이동만으로 전체 데이터를 다시 만드는 것을 피하기 위한 것이다. 개발 모드의 추가 실행 등은 가능하므로 정확히 한 번만 실행된다는 보장으로 이해하지 않는다.

## 4. 핵심 네 줄

```tsx
const totalPages = Math.ceil(items.length / pageSize);
const start = (page - 1) * pageSize;
const end = Math.min(start + pageSize, items.length);
const pageItems = items.slice(start, end);
```

데이터 23개, 페이지당 10개를 기준으로 계산해보자.

```text
1페이지:  1~10번째 데이터
2페이지: 11~20번째 데이터
3페이지: 21~23번째 데이터
```

### 4-1. totalPages: 몇 개의 페이지가 필요한가?

```tsx
Math.ceil(23 / 10); // 3
```

23 ÷ 10 = 2.3이다. 두 페이지를 채우고 남은 3개를 담을 페이지가 하나 더 필요하므로 올림한다.

| 데이터 수 | 페이지당 개수 | 나눗셈 | totalPages |
|---|---|---|---|
| 20 | 10 | 2 | 2 |
| 21 | 10 | 2.1 | 3 |
| 23 | 10 | 2.3 | 3 |
| 5 | 10 | 0.5 | 1 |

floor로 내리면 남은 데이터가 있는 마지막 페이지를 놓친다. round로 반올림해도 2.3이 2가 되어 맞지 않는다. 나누어떨어지는 경우에는 ceil을 해도 값이 그대로다.

### 4-2. start: 앞에서 몇 개를 건너뛸까?

```tsx
const start = (page - 1) * pageSize;
```

page - 1은 현재 페이지 앞에 있는 페이지의 수다. 여기에 페이지당 개수를 곱하면 앞에서 건너뛸 데이터 수가 된다.

```text
2페이지 앞에는 1페이지가 있다.
1페이지에는 10개가 있다.
따라서 앞의 10개를 건너뛴다.
첫 선택 위치는 인덱스 10이다.
```

| page | page - 1 | start |
|---|---|---|
| 1 | 0 | 0 |
| 2 | 1 | 10 |
| 3 | 2 | 20 |

page × pageSize로 계산하면 첫 페이지부터 인덱스 10에서 시작해 처음 10개를 건너뛰게 된다. 그래서 -1이 필요하다.

### 4-3. end: 시작점에서 몇 개를 선택할까?

```tsx
const end = Math.min(start + pageSize, items.length);
```

먼저 start + pageSize로 한 페이지 분량의 끝 경계를 만든다. 그런 다음 전체 배열 길이를 넘지 않도록 작은 값을 선택한다.

```tsx
// 2페이지
Math.min(10 + 10, 23); // 20

// 3페이지
Math.min(20 + 10, 23); // 23
```

3페이지에는 3개만 남았다. 실제 데이터는 인덱스 22까지 있지만, end는 23이다. end는 마지막 인덱스가 아니라 그 다음 경계이기 때문이다.

### 4-4. end를 왜 포함하지 않을까?

JavaScript slice가 시작 포함·끝 미포함 규칙을 사용한다.

```tsx
items.slice(10, 20); // 인덱스 10~19
```

경계 사이의 칸을 선택한다고 생각하면 쉽다.

```text
경계 10  [인덱스 10]  11  [인덱스 11]  ...  [인덱스 19]  경계 20
```

이 규칙에는 두 가지 편리함이 있다.

- 선택 개수는 end - start로 계산된다. 20 - 10 = 10개.
- 이전 페이지의 end가 다음 페이지의 start가 된다. 중복되거나 빠지는 항목이 없다.

```tsx
items.slice(0, 10);  // 첫 10개
items.slice(10, 20); // 다음 10개
items.slice(20, 23); // 마지막 3개
```

만약 두 번째 페이지를 slice(10, 19)로 쓰면 인덱스 18까지만 선택되어 9개가 나온다. 마지막 인덱스와 끝 경계를 혼동하지 않는다.

### 4-5. Math.min 없이 slice해도 될까?

slice 자체는 배열 길이를 넘는 끝 값을 처리한다.

```tsx
items.slice(20, 30); // 길이가 23이면 인덱스 20~22만 반환
```

하지만 이 실습은 end를 화면에도 표시한다. 30을 그대로 표시하면 실제로 없는 30번째 데이터까지 보이는 것처럼 안내하게 된다. Math.min으로 end를 제한하면 데이터 선택과 화면 설명 모두 실제 범위와 일치한다.

### 전체 결과

| 페이지 | start | end | 인덱스 | 화면 순번 | 행 수 |
|---|---|---|---|---|---|
| 1 | 0 | 10 | 0~9 | 1~10 | 10 |
| 2 | 10 | 20 | 10~19 | 11~20 | 10 |
| 3 | 20 | 23 | 20~22 | 21~23 | 3 |

화면 표시가 start + 1부터 end까지인 이유도 여기 있다. 마지막 선택 인덱스는 end - 1이므로, 이를 1부터 세는 순번으로 바꾸면 end가 된다.

## 5. 버튼 클릭부터 화면 변경까지

```text
처음 페이지 진입
 → page 1, pageSize 20, count 1,000으로 시작
 → 전체 items 생성
 → totalPages 50, start 0, end 20 계산
 → slice(0, 20)
 → map으로 첫 20개 행 렌더링
```

다음 버튼은 다음 코드를 실행한다.

```tsx
onClick={() => goToPage(page + 1)}
```

```text
goToPage(2)
 → setPage(2)
 → React가 갱신을 예약하고 컴포넌트를 다시 실행
 → start 20, end 40 계산
 → slice(20, 40)
 → 21~40번째 데이터 렌더링
```

setPage를 호출했다고 현재 실행 중인 함수 안의 page 변수가 즉시 바뀌는 것은 아니다. 다음 렌더링에서 새 상태를 읽는다.

start, end, totalPages, pageItems는 상태로 따로 저장하지 않는다. page, pageSize, items만 알면 계산할 수 있는 파생 값이므로 렌더링할 때 계산한다. 이를 각각 state로 저장하면 서로 맞지 않는 상태를 관리해야 할 수 있다.

## 6. goToPage의 경계 제한

```tsx
function goToPage(nextPage: number) {
  setPage(Math.max(1, Math.min(nextPage, totalPages)));
}
```

총 3페이지라고 가정하면:

```text
nextPage 4 → min(4, 3) = 3 → max(1, 3) = 3
nextPage 0 → min(0, 3) = 0 → max(1, 0) = 1
nextPage 2 → min(2, 3) = 2 → max(1, 2) = 2
```

유효한 1~3 범위를 벗어나지 않도록 제한한다. 이런 처리를 범위 제한 또는 clamp라고 부른다.

이전·처음 버튼은 page === 1일 때, 다음·마지막 버튼은 page === totalPages일 때 disabled가 된다. 버튼 비활성화는 사용자에게 경계를 보여주고, goToPage의 제한은 함수 내부에서 범위를 지킨다.

현재 함수는 내부 버튼에서 정수를 전달한다는 전제다. 자유 입력을 추가하면 빈 문자열, NaN, 소수 등의 입력 검증도 필요하다.

## 7. 페이지 번호 버튼도 범위를 따로 계산한다

```tsx
const firstPageButton = Math.max(1, Math.min(page - 2, totalPages - 4));
const pageNumbers = Array.from(
  { length: Math.min(5, totalPages) },
  (_, index) => firstPageButton + index,
);
```

여기는 실제 데이터 선택이 아니라 최대 5개의 번호 버튼을 만드는 계산이다.

- page - 2: 가능하면 현재 페이지 앞에 버튼 두 개를 둔다.
- totalPages - 4: 버튼 5개가 마지막 페이지를 넘지 않는 최대 시작 번호다.
- Math.max(1, ...): 시작 버튼 번호를 최소 1로 제한한다.
- Math.min(5, totalPages): 총 페이지가 5보다 적으면 있는 만큼만 만든다.

총 10페이지라면:

| 현재 page | firstPageButton | pageNumbers |
|---|---|---|
| 1 | 1 | 1, 2, 3, 4, 5 |
| 5 | 3 | 3, 4, 5, 6, 7 |
| 10 | 6 | 6, 7, 8, 9, 10 |

총 3페이지라면 버튼은 항상 1, 2, 3이다.

**pageNumbers는 버튼 번호, pageItems는 실제 콘텐츠다.** 이 둘을 혼동하지 않는다.

## 8. 데이터 수나 페이지 크기가 바뀌면 왜 첫 페이지로 갈까?

현재 코드는 count 또는 pageSize를 변경할 때 setPage(1)도 호출한다.

예를 들어 1,000개를 10개씩 보며 100페이지에 있다가 페이지당 50개로 바꾸면 전체 페이지는 20개가 된다. 기존 100페이지를 유지하면 slice가 빈 배열을 반환한다.

이 실습은 이해하기 쉬운 정책으로 첫 페이지로 돌아간다. 다른 서비스에서는 유효한 마지막 페이지로 제한하거나 현재 보고 있던 항목이 들어 있는 페이지를 유지할 수도 있다.

select에서 받은 event.target.value는 문자열이므로 Number로 숫자로 변환한다.

## 9. 가상화·서버 페이지네이션과 비교

| 항목 | 클라이언트 페이지네이션 | 가상화 | 서버 페이지네이션 |
|---|---|---|---|
| 선택 기준 | 페이지 번호 | 스크롤 위치와 크기 | API에 요청한 구간 |
| 데이터 보관 | 전체 배열 | 가져온 데이터 배열 | 받은 페이지 데이터 |
| 렌더링 | 현재 페이지 행 | 화면 주변 행 | 보통 받은 페이지 행 |
| absolute·좌표 배치 | 필요 없음 | 구현 방식에 따라 사용 | 페이지네이션 자체에는 불필요 |
| 초기 전송량 감소 | 전체 조회라면 불가능 | 가상화 자체로는 불가능 | 필요한 구간만 받으면 가능 |

현재 행은 일반 ul/li 흐름으로 쌓인다. 고정 ROW_HEIGHT나 VIEWPORT_HEIGHT 없이 내용에 따라 높이가 달라도 기본 페이지 계산에는 영향이 없다.

페이지네이션도 페이지당 수천 개를 표시하면 렌더링 부담이 클 수 있다. 필요한 경우 현재 페이지 안에 가상화를 함께 적용할 수 있다.

TanStack Virtual은 가상화를 담당한다. 페이지네이션 라이브러리 비교가 필요하다면 TanStack Table처럼 별도의 페이지네이션 기능을 제공하는 도구를 살펴볼 수 있지만, 기본 원리 학습에는 React 상태와 slice만으로 충분하다.

## 10. 현재 구현의 전제와 확장 시 주의점

- 데이터 개수 선택지는 23, 1,000, 10,000이므로 빈 목록이 없는 실습이다.
- pageSize는 10, 20, 50 중 하나로 항상 양의 정수다.
- page는 1~totalPages 안에 있도록 관리한다.
- 검색·정렬은 아직 구현하지 않았다.

검색을 추가할 때는 일반적으로 전체 배열을 필터링·정렬한 뒤 그 결과를 기준으로 totalPages와 slice를 계산한다. 현재 페이지를 먼저 자르고 검색하면 다른 페이지에 있는 검색 결과를 놓친다.

검색 결과가 0개일 수 있게 확장한다면 별도 처리가 필요하다. ceil(0 / pageSize)는 0이고 현재 UI의 start + 1 표시는 1이 되므로 그대로 쓰면 어색한 범위가 나온다. 빈 결과 메시지, 페이지 버튼 비활성화, 0개 범위 표시 등을 함께 설계한다. 현재 코드가 빈 결과까지 완성된 구현은 아니다.

## 11. 직접 실험하기

1. 데이터 23개·페이지당 10개로 설정한다.
2. 다음 버튼을 누를 때 start/end가 0/10 → 10/20 → 20/23으로 바뀌는지 본다.
3. 마지막 페이지의 행이 3개인지 확인한다.
4. 페이지당 20개로 바꾸면 첫 페이지로 돌아오고 총 2페이지가 되는지 본다.
5. 데이터 10,000개로 바꿔도 현재 페이지의 행 수만 DOM에 있는지 DevTools에서 data-list="pagination"을 확인한다.

slice 자체가 특별한 성능 최적화 API는 아니다. 전체 데이터를 DOM으로 만들지 않고 pageItems만 map으로 렌더링하는 것이 렌더링 부담을 줄이는 핵심이다.
