# 라이브러리 없이 이해하는 React 리스트 가상화

학습일: 2026-09-29  
실습 코드: [virtualization-lab.tsx](./virtualization-lab.tsx)  
실습 주소: `/demo/virtualization`

## 1. 공부를 시작한 질문

“데이터가 10,000개 이상이고 백엔드에서 한도 제한을 푼다면 어떻게 하실 건가요?”라는 질문을 들었다.

이 질문에 가상화가 답이 될 수 있지만, 먼저 어떤 비용이 문제인지 구분해야 한다.

```text
서버 조회 → 데이터 전송 → JSON 해석·배열 보관 → React 렌더링 → DOM 반영·레이아웃·페인트
```

가상화는 이 중 화면에 만드는 행을 줄여 렌더링 부담을 낮추는 방법이다. 같은 API에서 10,000개를 전부 받는 조건이라면 다운로드와 데이터 배열의 메모리 비용은 그대로다. DOM 관련 메모리는 줄일 수 있다.

현재 실습은 API 요청 없이 가짜 데이터를 생성하므로 네트워크 성능을 측정하는 예제가 아니다.

## 2. 가상화의 핵심 원리

전체 데이터는 배열로 가지고 있지만, 화면에 보이는 행과 앞뒤 여유분만 DOM에 만든다. 화면 밖의 행을 CSS로 숨겨두는 방식이 아니다.

```text
데이터 배열: 10,000개
목록 영역: 384px
행 높이: 64px
정렬된 위치에서 보이는 행: 6개
앞뒤 여유분: 각각 3개
목록 중간에서 렌더링하는 행: 12개 정도
```

행 중간에 걸쳐 스크롤하면 7개 행이 일부 또는 전부 보이므로 여유분까지 13개가 될 수 있다. 목록 시작과 끝에서는 여유분이 잘리므로 개수가 더 적다.

부모에는 전체 목록 높이를 유지하고, 선택한 행만 원래 좌표에 배치한다.

```text
사용자 스크롤
  → scrollTop 갱신
  → 필요한 인덱스 범위 계산
  → 해당 데이터만 선택
  → Row 렌더링
  → 각 행을 전체 목록에서의 원래 위치에 배치
```

## 3. 변수와 함수 사전

### 공통 값과 데이터

| 이름                 | 현재 값 또는 역할                                  |
| -------------------- | -------------------------------------------------- |
| `ROW_HEIGHT`         | 행 하나의 고정 높이. 현재 64px                     |
| `VIEWPORT_HEIGHT`    | 스크롤 영역에 지정한 높이. 현재 384px              |
| `format(value)`      | 숫자를 표시용 문자열로 변환. `10000` → `"10,000"`  |
| `buttonClass`        | 버튼들이 공유하는 CSS 클래스 문자열                |
| `createItems(count)` | 지정한 개수만큼 실습용 mock data 생성              |
| `Item`               | 생성된 배열의 요소 하나에 해당하는 TypeScript 타입 |

```tsx
const format = (value: number) => value.toLocaleString("en-US");
```

미국 영어 숫자 표기 규칙으로 변환한다. 원래 숫자를 바꾸지 않으며 반환값은 문자열이다. 가상화 계산과는 관계없다.

```tsx
Array.from({ length: count }, (_, index) => ({
  id: index + 1,
  title: `실습 데이터 ${index + 1}`,
  category: ["React", "TypeScript", "Next.js"][index % 3],
}));
```

`index`는 0부터 시작하고 `id`는 1부터 시작한다. `% 3`의 결과가 0, 1, 2를 반복하므로 카테고리도 순환한다.

```tsx
type Item = ReturnType<typeof createItems>[number];
```

`ReturnType`으로 함수의 반환 배열 타입을 얻고, `[number]`로 그 배열의 요소 타입을 얻는다.

### VirtualizationLab의 상태

| 이름                       | 역할                                           |
| -------------------------- | ---------------------------------------------- |
| `count` / `setCount`       | 데이터 개수와 변경 함수. 초기 1,000개          |
| `overscan` / `setOverscan` | 화면 앞뒤에 추가로 렌더링할 행 수. 초기 3      |
| `mode` / `setMode`         | `both`, `normal`, `virtual` 보기 선택          |
| `run` / `setRun`           | 다시 마운트 버튼을 누를 때 증가하는 값         |
| `items`                    | `createItems(count)`로 생성한 전체 데이터 배열 |

```tsx
const items = useMemo(() => createItems(count), [count]);
```

일반적인 재렌더링에서는 `count`가 같으면 계산 결과를 재사용한다. overscan 변경만으로 전체 배열을 다시 만드는 일을 피하기 위한 것이다. 가상화와 별개의 최적화이며, 개발 모드에서는 순수성 확인을 위해 계산이 추가 실행될 수 있다.

### ListExperiment의 값

| 이름             | 역할                                             |
| ---------------- | ------------------------------------------------ |
| `items`          | 부모에게서 받은 전체 데이터 배열                 |
| `virtual`        | 가상화 여부. `false`면 전체 행을 선택            |
| `overscan`       | 위아래에 미리 준비할 행 수                       |
| `viewport`       | 스크롤 컨테이너 DOM을 가리키는 ref               |
| `scrollTop`      | 컨테이너 안에서 위로 지나간 거리(px)             |
| `setScrollTop`   | 스크롤 거리를 상태에 반영하는 함수               |
| `firstVisible`   | 첫 번째로 보이는 행의 인덱스                     |
| `visibleEnd`     | 보이는 범위의 끝 경계. 이 인덱스는 포함하지 않음 |
| `start`          | overscan을 포함한 시작 인덱스. 포함              |
| `end`            | overscan을 포함한 끝 경계. 미포함                |
| `renderedItems`  | 실제 Row로 렌더링할 데이터 배열                  |
| `jump(position)` | 컨테이너를 주어진 세로 위치로 스크롤             |

### Row의 props

| 이름      | 역할                                |
| --------- | ----------------------------------- |
| `item`    | 행 하나의 데이터                    |
| `total`   | 전체 항목 수. `aria-setsize`에 사용 |
| `virtual` | 가상화 배치를 적용할지 결정         |

`role="listitem"`, `aria-posinset`, `aria-setsize`는 목록의 의미와 전체 목록에서의 위치를 보조 기술에 전달한다. 이것만으로 가상 목록의 접근성 처리가 모두 끝나는 것은 아니다.

## 4. 핵심 계산식: 위치를 인덱스로 바꾸기

```tsx
const firstVisible = Math.floor(scrollTop / ROW_HEIGHT);
const visibleEnd = Math.min(items.length, Math.ceil((scrollTop + VIEWPORT_HEIGHT) / ROW_HEIGHT));
const start = virtual ? Math.max(0, firstVisible - overscan) : 0;
const end = virtual ? Math.min(items.length, visibleEnd + overscan) : items.length;
const renderedItems = items.slice(start, end);
```

특별한 이름이 있는 공식보다는, 일정한 크기의 구간에서 위치를 찾는 계산이다.

```text
위치 ÷ 한 칸의 크기 = 몇 번째 칸에 있는지
```

### 쉬운 숫자로 계산하기

행 높이 100px, 영역 높이 300px, scrollTop 150px, 데이터 100개라고 가정한다.

| 인덱스 | 행이 차지하는 위치  |
| ------ | ------------------- |
| 0      | 0 이상 100px 미만   |
| 1      | 100 이상 200px 미만 |
| 2      | 200 이상 300px 미만 |
| 3      | 300 이상 400px 미만 |
| 4      | 400 이상 500px 미만 |

화면이 보여주는 구간은 150~450px이다.

```text
┌── 화면 위: 150px ──────┐
│ 인덱스 1의 아래쪽 절반   │
│ 인덱스 2 전체           │
│ 인덱스 3 전체           │
│ 인덱스 4의 위쪽 절반     │
└── 화면 아래: 450px ────┘
```

#### ① 첫 번째 보이는 행: floor

```tsx
Math.floor(150 / 100); // 1
```

150px은 인덱스 1의 행 안에 있다. 일부라도 보이는 첫 행을 포함하려고 내림한다. 반올림해서 2로 만들면 1번 행을 놓친다.

#### ② 끝 경계: ceil

```tsx
Math.ceil((150 + 300) / 100); // 5
```

끝 경계 5는 포함하지 않는다. `slice(1, 5)`가 인덱스 1, 2, 3, 4를 선택하기 때문이다. 아래에 일부만 걸친 4번 행도 포함하려고 올림한다.

화면 아래가 정확히 400px이면 `ceil(400 / 100) = 4`다. 4번 행은 400px부터 시작하므로 아직 보이지 않고, 인덱스 3까지 선택하면 된다.

`Math.min(items.length, ...)`은 끝 경계가 데이터 개수를 넘지 않게 한다.

#### ③ Overscan 추가

overscan이 1이라면:

```tsx
start = Math.max(0, 1 - 1); // 0
end = Math.min(100, 5 + 1); // 6
items.slice(0, 6); // 인덱스 0~5
```

인덱스 1~4는 보이는 행, 0과 5는 여유분이다. overscan은 스크롤할 때 다음 행이 미리 준비되도록 돕는다. 너무 크게 설정하면 렌더링 비용이 늘어난다.

`Math.max(0, ...)`은 시작 인덱스가 음수가 되는 것을 막는다. 예를 들어 맨 위에서 `0 - 3`을 그대로 slice에 전달하면 음수 인덱스가 배열 끝 기준으로 해석되므로 의도와 달라진다.

#### ④ Slice의 의미

`slice(start, end)`는 시작을 포함하고 끝을 제외한다. 원본 배열을 바꾸지 않고 선택한 구간을 새 배열로 반환한다. 내부 객체를 깊게 복사하는 것은 아니다.

가상화가 꺼져 있으면 `start = 0`, `end = items.length`라서 전체 배열을 선택한다.

### 현재 코드의 숫자로 계산하기

데이터 1,000개 이상, scrollTop 640px, 행 64px, 영역 384px, overscan 3:

```tsx
firstVisible = Math.floor(640 / 64); // 10
visibleEnd = Math.ceil((640 + 384) / 64); // 16
start = Math.max(0, 10 - 3); // 7
end = Math.min(items.length, 16 + 3); // 19
renderedItems = items.slice(7, 19); // 인덱스 7~18, 12개
```

보이는 행은 인덱스 10~15이고, 위아래 3개씩 더 렌더링한다.

### 행 높이가 홀수라면?

홀수여도 문제없다. 행 65px, 영역 300px, scrollTop 150px, overscan 0이라면:

```tsx
firstVisible = Math.floor(150 / 65); // 2
visibleEnd = Math.ceil((150 + 300) / 65); // 7
items.slice(2, 7); // 인덱스 2~6
```

나누어떨어지지 않는 상황을 처리하는 것이 floor와 ceil이다. 중요한 것은 짝수·홀수가 아니라 실제 행 높이와 계산에 사용하는 높이의 일치다.

## 5. absolute와 translateY가 필요한 이유

앞의 행들을 DOM에서 생략했으므로, 선택한 행을 일반 흐름대로 쌓으면 목록 맨 위에서 시작한다. 예를 들어 인덱스 10부터 렌더링해도 첫 DOM 행은 0px에 놓인다.

현재 구현은 모든 선택된 행에 공통 기준점을 주고 원래 좌표로 이동시킨다.

```tsx
{
  position: "absolute",
  top: 0,
  left: 0,
  width: "100%",
  transform: `translateY(${(item.id - 1) * ROW_HEIGHT}px)`
}
```

```text
인덱스 10 → 0 + 640px → 640px에 배치
인덱스 11 → 0 + 704px → 704px에 배치
인덱스 12 → 0 + 768px → 768px에 배치
```

absolute 없이 transform만 쓰면 일반 흐름에서 쌓인 위치에 이동량까지 더해진다. 두 번째 DOM 행은 원래 64px에 있는데 704px을 더해 768px에 놓이므로 잘못된 간격이 생긴다.

부모의 역할도 중요하다.

```tsx
style={{
  height: items.length * ROW_HEIGHT,
  position: "relative",
}}
```

- `relative`: absolute 행의 위치 기준을 제공한다.
- 전체 높이: 일부 행만 있어도 전체 목록의 스크롤 공간을 유지한다.

**translateY는 스크롤 위치를 변경하지 않는다. 각 행의 배치 위치를 정한다.** 실제 스크롤 이동은 사용자 입력이나 `jump()`의 `scrollTo()`가 담당한다.

가상화에 absolute가 필수인 것은 아니다. 생략한 구간만큼 위아래 빈 공간을 두는 방식도 가능하다. 현재 실습은 좌표 배치 방식이다.

### ID를 인덱스로 사용하는 현재 코드의 전제

`item.id - 1`이 인덱스와 같은 이유는 데이터가 1부터 순서대로 생성되고 정렬·필터링되지 않았기 때문이다.

정렬·필터링을 추가한다면 ID로 위치를 계산하면 안 된다. 선택한 배열에서의 순번이 `localIndex`라면 전체 현재 목록의 인덱스는 `start + localIndex`다. 이를 Row에 전달해 배치해야 한다. `aria-posinset`도 현재 목록 순서에 맞춰야 한다. React의 `key`에는 안정적인 ID를 계속 사용할 수 있다.

## 6. 반응형, padding, border, 유동 높이

현재 구현은 고정 크기를 전제로 한다. 실제 크기와 계산값이 달라지면 겹침, 빈 공간, 렌더링 범위 오류가 생길 수 있다.

| 상황                       | 확인할 점                                                    |
| -------------------------- | ------------------------------------------------------------ |
| 행의 padding·border        | `border-box`라면 지정 높이에 포함되지만 content-box는 더해짐 |
| 행의 세로 margin·별도 간격 | 현재 좌표 계산에는 포함되어 있지 않음                        |
| 긴 텍스트·이미지           | 고정 높이 안에 담기지 않으면 넘칠 수 있음                    |
| 컨테이너 크기 변경         | 실제 보이는 높이를 계산에 반영해야 함                        |
| 행 높이가 제각각           | 인덱스 × 고정 높이 공식을 사용할 수 없음                     |

현재 Tailwind 기본 box-sizing에서는 행의 border가 64px 안에 포함된다. 다만 스크롤 컨테이너의 `border-t` 역시 지정한 384px 안에 포함되므로 실제 내부 높이는 명목상 높이와 조금 다를 수 있다. 일반화된 구현에서는 `clientHeight` 등 실제 스크롤 영역 치수를 기준으로 삼고 크기 변경을 관찰하는 편이 정확하다.

absolute 요소도 콘텐츠에 따라 높이가 달라질 수 있다. 어려운 부분은 높이 변화에 맞춰 뒤 행의 좌표와 전체 높이를 다시 계산하는 일이다.

```text
행 높이:    64px, 100px, 80px
시작 위치:   0px,  64px, 164px
```

반응형에서 줄바꿈이 바뀌거나 이미지가 로딩되면 측정값도 달라진다. 동적 높이를 지원하는 가상화 라이브러리는 예상 크기, 실제 크기 측정, 위치 보정 등의 작업을 돕는다. 모든 라이브러리가 같은 기능이나 배치 방식을 제공하는 것은 아니다.

TanStack Virtual의 동적 높이 예제에서는 `estimateSize`로 예상 크기를 제공하고 `measureElement`를 행에 연결한다. 실제 적용 시에는 사용하는 버전의 문서를 확인한다.

## 7. 전체 코드 흐름

### 처음 페이지를 열 때

1. `page.tsx`가 `VirtualizationLab`을 렌더링한다.
2. count 1,000, overscan 3, mode both, run 0으로 시작한다.
3. `createItems`가 전체 배열을 만들고 `useMemo`가 결과를 재사용한다.
4. 두 `ListExperiment`에 같은 배열을 전달한다.
5. 각 목록은 독립적인 viewport ref와 scrollTop 상태를 가진다.
6. 일반 목록은 전체 1,000개, 가상 목록은 처음 보이는 6개와 아래 여유분 3개를 선택한다.
7. `renderedItems.map()`으로 각 Row를 만든다.

### 스크롤할 때

```tsx
onScroll={(event) => setScrollTop(event.currentTarget.scrollTop)}
```

해당 목록의 상태가 바뀌고 범위를 다시 계산한다. 이전 범위 밖의 행은 제거되고 필요한 행이 생성된다. 겹치는 범위의 행은 같은 key를 기준으로 React가 재사용할 수 있다. 두 목록의 스크롤은 동기화되어 있지 않다.

### 설정을 바꿀 때

```tsx
key={`${count}-${mode}-${run}`}
```

- count 변경: 배열이 새로 생성되고 목록이 다시 마운트된다.
- mode 변경: 선택한 보기로 목록이 다시 마운트된다.
- run 증가: 목록을 다시 마운트해 스크롤 상태를 초기화한다. count가 같으면 데이터 생성까지 다시 하는 버튼은 아니다.
- overscan 변경: key가 같으므로 스크롤 위치를 유지하면서 렌더링 범위가 바뀐다.

### 이동 버튼

`viewport.current?.scrollTo()`로 컨테이너를 이동한다. 마지막 버튼은 전체 높이를 요청하지만 브라우저가 실제 최대 스크롤 위치로 제한한다. 그 결과 발생하는 스크롤 이벤트가 상태와 렌더링 범위를 갱신한다.

## 8. 실제 API와 가상화의 관계

데이터를 가져오는 범위와 DOM에 렌더링하는 범위는 별개다.

### 전체 조회 API

```text
API에서 10,000개 받음
  → items 배열에 보관
  → 화면 주변 데이터만 선택
  → 일부 행 렌더링
```

현재 createItems 자리에 API에서 받은 배열이 들어오는 구조다. 초기 데이터 전송과 JSON 처리 비용은 가상화만으로 줄어들지 않는다.

### 서버 페이지네이션 + 무한 스크롤 + 가상화

```text
처음 50개 요청 → 배열에 보관 → 화면 주변만 렌더링
끝에 가까워짐 → 다음 50개 요청 → 배열에 누적 → 화면 주변만 렌더링
```

서버에 10,000개, 현재 받은 배열에는 150개, DOM에는 12개가 있는 상황이 가능하다. 로딩·실패·중복 요청 방지·다음 페이지 유무 등의 처리는 별도로 필요하다.

누적하다 보면 데이터 배열은 결국 커질 수 있다. 배열 메모리까지 제한하려면 오래된 페이지를 버리고 필요할 때 다시 요청하는 전략 등이 추가로 필요하다. 아직 받지 않은 마지막 데이터로 바로 이동하려면 API도 해당 구간 조회를 지원해야 한다.

## 9. 클라이언트 페이지네이션과 비교

클라이언트 페이지네이션은 전체 배열을 받은 뒤 프론트에서 페이지를 나눈다.

```tsx
const page = 2;
const pageSize = 50;
const start = (page - 1) * pageSize;
const pageItems = items.slice(start, start + pageSize);
// 인덱스 50~99: 51~100번째 데이터
```

| 방식                    | 구간을 결정하는 기준                | 초기 전체 다운로드를 줄이는가? |
| ----------------------- | ----------------------------------- | ------------------------------ |
| 클라이언트 페이지네이션 | 페이지 번호와 페이지당 개수         | 아니요                         |
| 서버 페이지네이션       | 서버에 요청한 page·offset·cursor 등 | 필요한 구간만 요청하면 가능    |
| 가상화                  | 스크롤 위치와 영역·행 크기          | 자체적으로는 아니요            |

`limit`은 한 번에 가져올 개수다. 다음 구간을 지정하려면 page, offset, cursor 등의 정보가 추가로 필요하다. 실제 파라미터 이름과 의미는 API마다 다르다.

서버 페이지네이션은 조회 방식이고, 무한 스크롤은 추가 내용을 불러오는 UX다. 둘을 가상화와 함께 사용할 수 있다.

## 10. slice 외의 메서드도 최적화에 쓰일까?

**slice 자체가 최적화 기능은 아니다. 선택한 데이터만 렌더링해서 DOM 생성을 줄인 것이 핵심이다.**

- `for`: start부터 end 전까지 직접 순회해 Row를 만들 수 있다. slice 중간 배열 없이 구현해도 가상화 원리는 같다.
- `filter`: 검색·카테고리 조건으로 데이터를 선택한다. 전체 배열을 검사하므로 검색 비용은 남는다. 필터링 후 가상화하면 행 위치는 새 목록 인덱스로 계산해야 한다.
- `Map`: ID로 반복 조회할 때 매번 배열을 탐색하는 일을 줄이는 데 유용하다. 생성 비용이 있으므로 만들어둔 Map을 재사용하는 상황에서 이점이 있다.
- `useMemo`: 같은 입력에 대한 계산 결과를 재사용하는 React 훅이다. DOM 개수를 자동으로 줄여주지는 않는다.
- 디바운스: 타이핑마다 검색·요청하는 횟수를 줄이는 기법이다. 배열 메서드는 아니다.

어떤 메서드를 쓸지보다 다운로드, 계산, 탐색, DOM 생성 중 어떤 작업이 병목인지 먼저 확인한다.

## 11. 직접 관찰하고 측정하기

1. 데이터 1,000개와 10,000개를 선택해 행 DOM 수를 비교한다.
2. 가상화 목록의 중간으로 이동해 범위가 바뀌는지 확인한다.
3. overscan을 0과 10으로 바꾸고 렌더링 개수를 관찰한다.
4. DevTools Elements에서 `data-list`의 `data-row` 자식 수를 확인한다. 화면의 카운트는 행 개수이며 자식 요소를 포함한 전체 DOM 노드 수가 아니다.
5. Performance에서 일반만 보기와 가상화만 보기를 각각 기록한다. 같은 데이터 수, CPU 조건, 이동 동작을 사용한다.
6. 최종 비교는 프로덕션 빌드로 하고 여러 번 측정한다. DOM 감소율이 실행 시간 감소율과 같다고 가정하지 않는다.

현재 일반 목록도 scrollTop 표시를 위해 스크롤마다 상태를 갱신하므로 전체 행의 React 렌더링 작업이 반복될 수 있다. 따라서 이 데모를 모든 일반 목록 구현의 성능을 대표하는 벤치마크로 해석하지 않는다. 코드에 있는 `console.log(items)`도 대량 로그 비용을 추가할 수 있으므로 엄밀한 측정에서는 제거하거나 비활성화한다.

## 12. 면접에서 설명한다면

> 먼저 응답 크기와 응답 시간, 프론트 렌더링 중 어느 부분이 병목인지 확인하겠습니다. 전체 데이터를 받아야 한다면 가상화나 클라이언트 페이지네이션으로 렌더링 범위를 제한하겠습니다. 가상화는 다운로드와 데이터 보관 비용까지 줄이지는 못하므로, API 변경이 가능하다면 서버 페이지네이션으로 필요한 구간만 요청하고 필요에 따라 가상화를 함께 적용하겠습니다.

데이터 개수만으로 무조건 같은 최적화를 결정하지 않는다. 행 UI의 복잡도, 데이터 크기, 검색·정렬 비용, 사용자의 탐색 방식에 따라 대응이 달라진다.
